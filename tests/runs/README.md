### D. 外部复核（`de592e7` 之后）— 3 件

**F3 → F13 → F14 是同一处规则的三次修正**，每一次的修法都引入了新的错误方式：

```
F3   只删标记      → 留下多余空格
F13  两侧空白全删  → 粘连英文术语、吃掉分词空格
F14  按字符类型补  → 数字紧邻被拆开、仍吃掉分词空格
现行 只删标记，空白调整作为单独的逐条复核编辑 → 不再让机械步骤猜排版
```

**教训是：这类问题不该靠更聪明的规则解决，该靠缩小机械步骤的职责范围。** 新稿一律用独占行标记，表格用外部映射，问题从源头消失。实测对照见 `2026-09-17-strip-rule.md`。

### F. 自验证收尾（全假名・英语场次）— 3 件

| # | 问题 |
|---|---|
| F18 | **全假名转写有三类陷阱**：同一汉字不同活用形读音不同（`出しました→だしました`／`出て→でて`）、同音异义（`しりょう＝資料/史料`，人文社科里是两个概念）、分かち書き是功能性空白。规则只写了"必须实际转写"，没写转写后会遇到什么 |
| F19 | **「英语场次不覆盖表达规范」是一刀切**，把语言无关的原则（一句一信息、术语首次解释、答不出时的三段框架、不过度断言）也一起丢掉了 |
| F20 | **日语特有的基准没有标注**：`280〜320 字/分`、危险词表。英语场次会被误用（分类语言无关、词表是日语） |

**F18・F19 是同一种病：规则写了、但从没执行过。**

> **一条规则只要没被执行过，它的边界就是想象出来的。**
> F12 写了"必须实际转写"——真转写了才知道有三类陷阱。
> 「英语场次不覆盖表达规范」写了很久——真按英语场次跑了，才发现这句话把不该切的也切掉了。

F15・F16 属同一类：规则覆盖了"说的内容对不对"，没覆盖"说的顺序与时机对不对"。

**F17 是这批里最实用的一条**，因为它是**核验者自己的**缺陷。`rehearsal-and-audit.md` 新增第零步：先固定现用版本清单与版本标识，写明本次未检查的部分；**结论的措辞受这份清单约束**。同时补了两条判据：**待办清单 ≠ 执行证据**、**四方缺一方就不能称四方核验**。

> **F15 初版写过严，当轮即被指出并修正**：原文写"机制未实装则一切动作例都要带设想标记"，但系统整体未完成不代表局部原型／仿真没有真实结果。改为按每个例子自己的证据判断。
> **把有实测的结果说成"设想"，和把设想说成结果一样是失真。** 这与 F11 是同一个毛病——规则写得太紧会把正确行为判成违规，**写 F15 时又犯了一次**。

### 关于本目录的证据效力

**没有一条记录是独立验证。** 三个夹具是为测这些规则而写的，真实材料是这些规则的经验来源。
本目录能证明的是"规则在这些场景下自洽、可执行、且发现过真问题"，**不能证明"规则在新的、未见过的申请人身上成立"**。

**核验者自己也会出错，错法可预期：选错版本、把估算当结果、把回查当独立验证。** 来源材料回查那轮三种全犯了，事后逐条更正。

### 三条最值得记住的教训

**F11：写得太紧的规则会把正确行为判成违规。** 脚本量出页面与口述有 3 处 12 字以上重叠，按字符级规则全是违规——但那三处是关键词和主语短语，恰恰是评委把画面和耳朵对上的锚点。

**F3 → F13 → F14：同一处规则连错三次，每次的"修复"都换了个出错方式。** "diff 只出现标记行"放过残留空白 → "两侧空白全删"粘连英文术语 → "按字符类型补空格"拆开数字、仍吃掉分词空格。更糟的是当时的验证方式——"按同一规则再剥离一次做比较"——是**自洽检查**，两边用同一条错规则必然一致，**在结构上不可能发现这个 bug**。

> 教训有三层：
> 1. 核验规则需要被核验。
> 2. **验证方法不能依赖被验证的那条规则本身**——要验证的是不变式（"非标记字符一个都没变"），不是"再跑一次结果一样"。
> 3. **连错三次说明方向就错了**：不该找更聪明的规则去猜排版，该**缩小机械步骤的职责**。新稿一律独占行标记，问题从源头消失。

**F17：结论的可信度，上限是核验时的版本纪律。** 只读了 11 个问答版本中的 1 个，就下"整个材料集缺失某内容"的结论——这个错误与规则本身无关，是**核验者的方法错误**。规则再好，用错版本也会得出错的结论。

## 关于仓库历史

**公开仓库从单个提交开始**，不含开发过程的历史，因此也不含开发期残留的本机路径。提交元数据含作者姓名与邮箱（许可证署名需要）。

开发历史（14 个提交）保留在作者的私有仓库里。**那份历史中的早期提交含本机绝对路径，以及一处被当作测试字符串误用的真实论文名**——这正是它没有被公开的原因。

> **教训**：整个开发过程里，每轮泄漏扫描都只扫了工作树，没扫 git 历史。
> **"当前树干净"不等于"仓库干净"。** 发布前必须扫历史（`git log -p --all | grep`），
> 而不只是扫文件（`grep -r`）。这个漏洞直到准备公开时才被发现。

## 怎么再跑一次

1. 读 `../fixtures/` 下的夹具，按 `SKILL.md` 执行 `--full`
2. 对照夹具末尾的检查点逐项判定
3. **写盘变体**：把产物写到 skill 仓库**之外**的临时目录，验泄漏防护与剥离 diff
4. 新记录按 `YYYY-MM-DD-<场景>.md` 命名，并在本文件的一览表里加一行

**发现新问题时，先修 skill，再在记录里写清问题与修法**——记录的价值在于说明为什么规则长成现在这样。
